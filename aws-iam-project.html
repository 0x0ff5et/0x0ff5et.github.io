Enhance Cloud Security with AWS IAM

A hands-on project separating Dev and Prod EC2 access using resource tags, least-privilege permissions, and positive and negative testing.

Quest stages0 of 5 cleared
  1. Launch EC2 instances
  2. Create an IAM policy
  3. Create an AWS account alias
  4. Create IAM users and user groups
  5. Test your intern’s access

Scenario: you’ve just joined a team as a DevOps engineer. There are two tasks. First, boost computing power to match increased traffic to the website. Second, onboard an intern, who should get the right permissions to contribute while the company’s resources stay secure.

Launch EC2 instances

Start with the first task and launch two EC2 instances: one for production and one for development.

  1. Log in to the AWS Management Console and open the EC2 console from the search bar.
  2. Switch your Region to the one closest to you.

In the EC2 console choose Launch instance and set up the production instance:

  • Name: amazon-prod-0x0ff5et
  • Add a tag with Key Env and Value production
  • AMI: a free tier eligible option; instance type: free tier eligible (t2.micro)
  • Key pair (login): Proceed without a key pair; network settings stay on their defaults
AWS shows a warning here: rules with source 0.0.0.0/0 allow all IP addresses to reach the instance. That is acceptable for a short lab, but restrict it to known IPs for anything real.

Launch it, then create one more instance for the development environment: Name amazon-dev-0x0ff5et with tag Env = development. Open Instances in the left navigation and refresh until both appear.

Select an instance and open the Tags tab to confirm the tags you defined.

Create an IAM policy

The intern should have permission on the development instance but not the production instance. You don’t want them to accidentally shut down the platform or push changes to production while they are just testing things.

  1. Open the IAM console and choose Policies, then Create policy.
  2. Switch the policy editor to JSON and replace all existing code with the policy below.
json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "ec2:ResourceTag/Env": "development"
        }
      }
    },
    {
      "Effect": "Allow",
      "Action": "ec2:Describe*",
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": [
        "ec2:DeleteTags",
        "ec2:CreateTags"
      ],
      "Resource": "*"
    }
  ]
}
  • Allow ec2:* only on resources tagged Env = development. The tag is what scopes the permission.
  • Allow ec2:Describe* on everything, so the intern can see instances in the console.
  • Deny create and delete tags, so the intern can’t retag a production instance as development and give themselves access. An explicit deny always wins.

Name it AmazonDevEnvironmentPolicy, with the description IAM Policy for Amazon development environment, then choose Create policy.

Create an AWS account alias

The intern can’t wait to start, so make the sign-in easier. In the IAM console open the Dashboard, choose Create under Account Alias, and enter the preferred alias:

text
amazon-alias-0x0ff5et

Your sign-in URL now uses the alias instead of the account ID, so it is much easier to find and log in.

Create IAM users and user groups

The new intern has no way to log in yet. You wouldn’t share your own account details, because you have access to the production instances and they shouldn’t.

  1. Choose User groups, then Create group. Name: amazon-dev-group. Attach AmazonDevEnvironmentPolicy, then create the group.
  2. Choose Users, then Create user. User name: amazondev0x0ff5et.
  3. Tick Provide user access to the AWS Management Console and uncheck Users must create a new password at next sign-in.
  4. On the permissions step add the user to amazon-dev-group, then choose Next and Create user.

Test your intern’s access

Before handing over the login, test the intern’s access. You want the right access to the development instance and none to production.

  1. Copy the console sign-in URL, keep that tab open, and open the URL in an incognito window.
  2. Sign in with the alias, the user name amazondev0x0ff5et and the console password.

Negative test: stop the production instance

In the EC2 console, in the same region, select the production instance and choose Instance state, then Stop instance.

Positive test: stop the development instance

Select amazon-dev-0x0ff5et, open Actions, then Manage instance state, choose Stop, and confirm.

Quest complete

The intern can stop the development instance and is denied on production. Tag-based conditions plus an explicit deny on tagging gave least privilege, and you proved it with both a positive and a negative test.
