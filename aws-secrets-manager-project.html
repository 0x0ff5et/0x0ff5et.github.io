Secure Secrets with AWS Secrets Manager

A practical walkthrough of replacing hardcoded AWS credentials with Secrets Manager, retrieving them in Python, and checking that sensitive values are removed from public code and Git history.

Quest stages0 of 5 cleared

  5. Step 5: Push changes

Applications use credentials and API keys to access AWS services and other resources. If exposed in source code, these secrets can lead to unauthorized access and data breaches. This project demonstrates secure credential management using AWS Secrets Manager.

What this project demonstrates

  • Identify insecure credential storage in a web application.
  • Test GitHub Secret Scanning to prevent credential leaks.
  • Use AWS Secrets Manager to securely store and retrieve credentials.
  • Verify that sensitive credentials are removed from public source code and Git history.

Project workflow

From cloning the original repository, to hardcoding credentials, to securing them and pushing the updated code to a forked repository on GitHub.

All credentials shown in this write-up are redacted. Never publish real access keys.

Step 1: Examine and set up the code

Take a look at a simple web app that lists S3 buckets, copy the code to your computer, and set it up with hardcoded AWS credentials.

Understand the application code

The repository holds an intentionally insecure web app that displays the names of S3 buckets in your AWS account. Open app.py, the main file with the logic of the app: how it responds to requests and talks to AWS.

Examine config.py

config.py holds the credentials that list_s3_buckets reads through config.AWS_ACCESS_KEY_ID, config.AWS_SECRET_ACCESS_KEY and config.AWS_REGION.

The security risk

The access key ID and secret access key are written directly in config.py. In a public GitHub repo, anyone could see them and use them to access your AWS account, delete resources, steal data and cause damage. It isn’t only AWS credentials: database passwords, API keys and any kind of secret should never be embedded in code.

Set up your local environment

bash
cd Documents
git clone https://github.com/nextwork-projects/nextwork-security-secretsmanager.git
cd nextwork-security-secretsmanager
ls

You should see app.py, config.py, Dockerfile and requirements.txt. Open config.py in an editor and replace the placeholders with example credentials (redacted here):

python
AWS_ACCESS_KEY_ID = "AKIAXXXXXXXXXXXXXXXX"
AWS_SECRET_ACCESS_KEY = "XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX"
AWS_REGION = "us-east-2"

Step 2: Make your code public

Fork the original repository: choose Fork, add a description such as A fork of an insecure web app that contains AWS credentials, and choose Create fork.

Push your code to GitHub

Stop the local app with CTRL + C, then connect your local repo to your fork and push.

bash
git init
git remote add origin https://github.com/0x0ff5et/nextwork-security-secretsmanager.git
git remote set-url origin https://github.com/0x0ff5et/nextwork-security-secretsmanager.git
git remote -v
git add .
git commit -m "Updated config.py with hardcoded credentials"
git push -u origin main

The push fails with “Push cannot contain secrets”. GitHub automatically scans your code for secrets and blocks the push if it detects any. Here it found an AWS Access Key ID and Secret Access Key in config.py, a great feature that prevents accidental exposure.

Step 3: Create a secret in Secrets Manager

GitHub rightly blocked the push. This is exactly why we need a dedicated service for managing secrets: AWS Secrets Manager. Store the credentials there, then update config.py to retrieve them instead of hardcoding them.

  1. Open the Secrets Manager console, select Secrets, then Store a new secret.
  2. Under Choose secret type select Other type of secret.
  3. Add the key AWS_ACCESS_KEY_ID, click Add row, and add the key AWS_SECRET_ACCESS_KEY.
  4. Paste each value from your config.py into the matching value field.
  5. Leave the encryption key as the default AWS managed key (aws/secretsmanager) and choose Next.

Then configure the secret:

  • Secret name: aws-access-key
  • Description: Created to replace hard-coded access key credentials in config.py
  • Skip tags, resource permissions, replication and rotation for now
  • Review: type Other type of secret, encryption aws/secretsmanager, replication Disabled, rotation Disabled

On the review page, the Sample code section shows exactly how to retrieve the secret in your application. Choose Store.

Step 4: Update config.py

A green banner confirms Successfully stored the secret. Select See sample code, open the Python 3 tab, and copy from the first import statement (line 6) to the end of the block.

Replace the entire config.py with that snippet, delete the # Your code goes here comment, and add import json at the top. The first two lines import boto3, the AWS SDK for Python, and ClientError from botocore to handle errors. get_secret() sets the secret name and region, creates a Secrets Manager client, and wraps the lookup in try...except. Make sure the region matches where you created the secret.

Finally, return the parsed secret and read the credential values from it. The finished config.py:

python
import boto3
from botocore.exceptions import ClientError
import json


def get_secret():
    secret_name = "aws-access-key"
    region_name = "ap-south-1"

    session = boto3.session.Session()
    client = session.client(
        service_name="secretsmanager",
        region_name=region_name
    )

    try:
        response = client.get_secret_value(SecretId=secret_name)
    except ClientError as e:
        raise e

    return json.loads(response["SecretString"])


credentials = get_secret()

AWS_ACCESS_KEY_ID = credentials.get("AWS_ACCESS_KEY_ID")
AWS_SECRET_ACCESS_KEY = credentials.get("AWS_SECRET_ACCESS_KEY")
AWS_REGION = credentials.get("AWS_REGION", "ap-south-1")

Step 5: Push changes

bash
git add .
git commit -m "Updated config.py with Secrets Manager credentials"
git push -u origin main

The push still fails with the same error. The old commit that introduced the hardcoded credentials is still in the Git history, and GitHub scans history too.

Remove hardcoded credentials from commit history

Use git rebase to rewrite history and drop the commit that introduced the credentials. First find that commit’s ID in your terminal history and note its first 7 digits. Then run:

bash
git rebase -i --root
  1. In the interactive editor, move to the commit with the credentials and change pick to d (drop) at the start of that line.
  2. Save and close the editor (:wq, then Enter). Git removes the commit from history.
  3. You may hit merge conflicts during the rebase.

Resolve merge conflicts

Open config.py. You’ll see conflict markers with the old hardcoded version above ======= and the new Secrets Manager version below it.

text

AWS_REGION = "us-east-2"
=======

import boto3
from botocore.exceptions import ClientError
import json

def get_secret():
    # ... rest of the Secrets Manager code ...
>>>>>>> ea89d6b (Updated config.py with Secrets Manager credentials)

Delete everything from <<<<<<< HEAD through =======, which removes the hardcoded credentials, then delete the closing >>>>>>> line. Save the file, then continue:

bash
git add config.py
git commit -m "Resolved merge conflicts"
git rebase --continue
git push

Verify your GitHub repository

  • Open your forked repo on GitHub and check config.py. It should be clean of hardcoded credentials and only contain the code to retrieve them from Secrets Manager.
  • Check the commit history of config.py. There should be no commit containing your hardcoded credentials.

Quest complete

The credentials live in Secrets Manager, config.py only knows how to fetch them, and the Git history no longer contains them. GitHub’s secret scanning accepted the push.
